# 設計判断ログ

このファイルには「なぜその設計にしたか」を記録する。コミットログには何を変えたかは残るが、
検討した代替案や却下した理由までは残らないため、後から経緯を追えるようにここに書く。

新しい判断を追記するときは、日付・決めたこと・理由・検討した代替案（あれば）の順で書く。
決定事項は基本的に上書きせず、方針転換した場合も「転換した」という記録として残す。

---

## アプリの位置づけ（前提）

正式な電子カルテ（anirece cloud）の代わりではなく、**それを補完する参照用メモ**。
既存カルテだと過去の薬歴・検査歴が時系列に埋もれて串刺しで追えないため、そこを補うのが目的。
iPad横向き専用、院内約8台で運用。

この位置づけから導かれる原則として、**電子カルテで足りることはこのアプリでやらない**。
検査値の推移表、会計、在庫、予約は対象外。新しい機能を検討するときは、まず
「それは電子カルテで足りるか」を問う。

## 2026-08-08 認証を匿名認証からメール/パスワード認証（院内共通アカウント）に切り替え

Firebaseから「安全でないルール」の警告メールが届いたことがきっかけ。匿名認証（`auth != null`）
のままではRealtime DatabaseのルールがUIDを絞れず、警告の解消にならないと判断。

- 院内共通アカウントを1つ作成し、DBルールをそのUIDに限定する方式にした。
- パスコード（2211）はFirebase認証の後段の入口として残した（認証の代わりではなく、認証後の
  簡易ロックとして位置づけを整理）。
- ロールアウト手順は `docs/AUTH-ROLLOUT.md` に分離。院内約8台の端末を止めずに切り替える必要が
  あり、匿名認証の無効化とルールのデプロイを「全端末ログイン完了後」まで遅らせる順序が重要
  だったため、手順書として独立させた。
- 共通アカウント運用を続ける前提で、退職者が出た際はパスワードを変更するルールとした
  （個別アカウント化は「今後の拡張候補」に留め、今回は見送り）。
- サインアウトは設定メニューの中だけに置き、実行時に管理者パスコードを要求する。共有iPadで
  誤って押されると、パスワードを知らないスタッフがその場で作業できなくなるため。

### 認証の関門で見つかった2つの穴（2026-08-11, `b690e65` / `b90eadb`）

- 端末に残った匿名セッションを「ログイン済み」と誤認する不具合。
- パスコード一致だけでFirebase認証の状態を確認せず本編へ通していた不具合。

**教訓**: 既存の `verify-email-auth` テストが `js/auth.js` ごとモックしていたため、両方の不具合を
素通りさせていた。対象モジュール自体をモックするテストは不具合を捉えられない。Firebase SDKだけ
差し替える `verify-auth-gate.mjs` を新設し、修正を戻すと検証が失敗することを確認する運用に変えた。

## 2026-08-10〜08-11 画面を「状態モード」「入力モード」「履歴（3カラム）」の3つに分離

**背景**: このアプリは本来「診察前に引き継ぎ状況や既往を一目で把握する」ためのものだったが、
実際には記入画面が中心の構成になっており、本末転倒だと感じたのがきっかけ。

- **状態モード**（`962e9d0`）: 既往歴・検査・薬剤・特記を1画面に展開し、診察前に一目で状況を
  把握できる画面として新設。
- **入力モード**（`464c909`）: 診察後にまとめて記録する専用の全画面。ChatGPTで整形した本文の
  貼り付けと、その日の薬・検査・処置の登録を1画面で完結させる設計。
- 記入は診察後にまとめて行う運用のため「参照しながら書く」場面が発生しない、という運用実態が
  この分離の前提。参照（状態・履歴）と記入（入力）を画面として分けることが成立する根拠になった。
- 状態モードと履歴モードは「裏表」の関係、そこに入力モードが付随する、という全体像を採用。

**進め方の原則**: いずれも「新しい画面を先に足す → 数日使う → 既存を整理する」の順で進めた。
既存に手を入れずに新規画面として追加すれば、合わなければ入口を戻すだけで済み、捨てるコストが
小さい。

## 2026-08-18 チップ検出の照合方式（AIを使わない文字列照合）を採用

入力モードで、貼り付けた本文からマスタ登録済みの薬剤名・検査名を検出してチップとして提示する
機能。AIによる自動判定ではなく、文字列照合（`58d8639` であいまい照合に緩和）を選んだ。

**理由**: 本文中を色付けする案より、検出候補が入力欄の下に一箇所にまとまる方が認識しやすいと
判断。またAI判定は精度・UIが安定しないリスクがあり、まず確実に動く文字列照合から始める方が
着地が早いと判断した。誤検出が増えてもよいので候補を多く出す方向に緩める、という方針
（誤検出は押さなければ実害がないが、取りこぼしは気づけないため実害が大きい、という非対称性）。

**関連**: 保存直後にAIが自動で提案するフロー（`ai-suggest-ui.js`）は精度・UIが安定せず、
実装を一旦見送っている。再開するなら保存をブロックせず、保存後に非同期で通知する形にする。
AI活用は「確実に効く場所から少しずつ」という温度感。

## 2026-08-21 検査・処置の運用フローを確定

実運用で「操作の順番が直感と合わない」「完了させると予定が消えて復活できない」という問題が
出たため、フロー全体を組み直した。

**予定をタップしたときの流れ**

1. 1枚目: 項目名・メモ（編集可）・実施日、その項目の**過去の実施履歴一覧**（新しい順、
   タップで編集・削除可）、そして「完了として保存」「終了として保存」の2択。
2. 2枚目（完了を選んだ場合のみ）: 次回予定のカレンダーと「次回予定を保存」。

**理由**: 「完了」を選ぶという行為自体が「実施した日がある」ことを前提にしているため、実施日は
1枚目に置くのが自然。逆に、完了か終了かを決める前に次回予定のカレンダーが見えていると、
何から操作すればいいか分からない。「終了」はもう追わない項目なので次回予定を聞かない。

**次回予定の指定方法**

- 「2〜3ヶ月後」のような幅で指定でき、「あと60日〜90日」と表示する。実際の診療では幅のある
  指示をすることが多いため。
- 色分け（緑/黄/橙/赤）は**終了日（遅い方＝本当の期限）を基準**に判定する。検査を忘れないと
  いう目的からすると、安全側に倒すのが正しいため。
- 相対日付の計算は**実施日を基準**にする。過去データの移行では過去日を実施日として入れるため、
  今日基準だと意図した日付にならない。
- 月換算は30日固定（既存仕様の踏襲）。

**入力方式の変遷**: 当初は相対テンキー（月→数字→確定）だったが、開始・終了の2回入力に
対応させた結果わかりにくくなり、実際に使ってみてテンキーの速さにメリットを感じなかったため、
**カレンダー2欄に一本化**した。ラベルは「開始／終了」だと入院期間などを連想させるため
「目安の始め／目安の終わり」に変更。

**継続と単発**: 実施記録を追加するとき「継続として記録」「単発として記録」を選べる。継続は
その項目の実施履歴に蓄積し、単発は中央カラムの時系列にその日の出来事として記録する。
継続的にフォローする検査と、1回で終わる検査では、残すべき場所が違うため。

**予定と実施履歴の重複表示をなくした**（`10c7653`）: 次回予定がある項目は実施履歴セクションに
表示しない。同じ項目が2箇所に出るのは冗長なため。過去の記録は予定をタップした1枚目で見られる。

## 2026-08-25〜09-05 マスタ階層選択からフリーワード入力への全面転換

既往歴（`b07693a`, 08-25）→ 検査・処置（`53d61ce`, 09-05）→ 薬剤（`a3db4eb`, 09-05）の順で、
大分類→中項目→小項目という階層マスタ選択方式を廃止し、サジェスト付きのフリーワード入力に
切り替えた。

**理由**: 実運用で入力コストの高さから薬剤・検査がほぼ使われず、記録（時系列）だけが使われて
いる状態が明らかになったため。階層をたどる操作が診療の合間の入力には重すぎると判断した。
**「階層は探す時の道具であって、入力のたびに通る関門にしない」**という原則に立ち返った形。

- 検査は絶食の選択欄も廃止し、必要な場合は「肝スク（絶食）」のように項目名に書く運用にした。
  マスタの `defaultFasting` はデータとしては残っているが、現在は使われていない。
- 薬剤はマスタ（422件）をサジェスト候補としては残した。新規登録時は「その患者の過去処方から
  候補を出す」という発想は当てはまらないため、マスタのシードデータを候補元として使い続ける。
- 薬剤の追加・編集からは頻度・投与量・開始日の入力を外し、期限とメモだけで済ませられる形に
  簡略化した（`021a3b4`）。期限を残したのは、アラート（期限が近づくと色が変わる）がシステム
  でないと実現できない価値だから。頻度や用量は書いておけば人が読めばよい情報なのでメモに回す。
- 種別（疾患／手術歴／紹介）、進行中／終了、カテゴリA/B/C、頓服マークは維持している。

**却下した代替案**: 検査値の構造化（フローシート形式での管理）はFableのレビューで提案されたが
不採用。電子カルテ（anirece cloud）側の検査履歴の表がすでに使えるため、このアプリで重複して
持つ必要はないと判断した。

## 2026-10-30 記録日と既往歴の開始日を8桁の手打ちにした

カレンダーから日付を選ぶのは手数が多く煩雑だった。`20261010` のように
8桁を打てば日付になるようにした。8桁が実在する日付になった時点で、欄の横に
`2026/10/10（土）` と曜日を出し、打ち間違いに気づけるようにする。存在しない日、
1990年より前、今日より先は、打っている途中では止めず、保存のときだけ止める。

対象は、1ページ構成に戻したあとも残る3欄だけにした。入力モードの記録日、
既往歴・特記を追加するときの開始日、その詳細の開始日（状態モードと右カラム）

## 開発体制についての判断

- **設計相談はClaude、実装はCursor**という分担。
- **モデルの使い分け**: 一時期Opusを常用した結果、2週間でCursor課金が約10万円に達したため、
  用途で使い分ける運用に変えた。原因不明の不具合調査・大きな設計判断はOpus、標準的な実装は
  Sonnet、定型作業（データ登録、期待値更新、色調整、表示追加）はGrok / Composer。指示を出す
  ときは冒頭に `[モデル名で]` と明記する。
- **テスト実行範囲**: 全件実行を繰り返したことがコスト増の主因だった。`AGENTS.md` に定めた
  とおり、全件実行は既定にしない。
- **コミットの分け方**: 性質の違う変更（実装／テスト基盤／セキュリティ修正）は別コミットに
  分ける。後から片方だけ戻せるようにするため。
- **節目でGitタグを打つ**（`beta1` → `beta1.1` → … → `beta2.6`）。大きな変更に入る前の
  基準点として、戻れる場所を作っておく。

## 2026-09-20 既往歴の種別は院内カルテと同じアイコンの複数選択にする

種別（疾患／手術歴／紹介）と状態（進行中／終了）を別々に持っていたが、院内電子カルテで長く使っている4つのアイコン（🚹現疾患／✅疾患歴／🚨手術／🔰紹介）に揃える。意味がスタッフに共有されているので、一覧はアイコンだけにして視認性を上げる。

「紹介先で手術をした」のように同時に複数の意味を持つことがあるため、単一選択ではなく複数選択にする。並びは 🚹 → ✅ → 🚨 → 🔰。複数付いた項目は、付いている中で一番早いアイコンのグループに置く。

既存データは消さない。`kinds` を足し、未設定なら旧 `type` / `status` から読む（疾患＋進行中→🚹、疾患＋終了→✅、手術歴→🚨、紹介→🔰）。保存時だけ `kinds` を書き、旧フィールドも主種別で同期する。

状態モードの一覧では、種別ごとの見出し行（🚹 / ✅ だけが並ぶ行）は出さない。各行の先頭アイコンと同じ記号が重複して見え、行の密度も落ちるため。並び順（当初は 🚹 → ✅ → 🚨 → 🔰）は見出しなしでも維持する。

## 2026-09-20 特記を既往歴と同じ列・同じアイコン選択に乗せる

種別をアイコンにしたので、特記も同じ仕組みに乗せて状態モードを3列にする。4列のままだと各列が細く、特記だけ別列なのがアイコン方針と食い違う。

特記のアイコンは ⚠️重要 と 💬特記。追加・編集は既往歴と同じボタンで、アイコンと文字を並べて複数選択する。並びは ⚠️ → 💬 → 🚹 → ✅ → 🚨 → 🔰。複数付いた項目は、付いている中で一番早いアイコンの位置に置く。

既存の特記は消さない。`specialNotes/` は残し、読み取り時に既往歴へ混ぜる（検査と処置のマージと同じ）。重要度「高」は ⚠️、「中」「低」は 💬。保存するときだけ `kinds` を書き、importance も同期する。新規の ⚠️／💬 は `history/` に書く。スワイプ削除・タイトル・開始日の編集は特記側でも同じ操作にする。

同じ列に乗せたあと、特記と既往歴の境目がアイコンだけでは分かりにくい。見出し行は出さず、⚠️💬 の群と 🚹✅🚨🔰 の群の間に細い線を1本だけ置く。余白は最小。片方の群しかないときは線も出さない。位置は並びと同じく主種別で決める。

## 商業化について

既存の商業電子カルテにない機能が作れている点を強みと考えているが、他院への展開は「今すぐ」では
なく、AI機能が安定し、アプリ全体が熟成してから検討する方針。優先順位としては院内での実運用の
安定を先に置く。他院展開に進む場合は、院内共通アカウント方式から個別アカウント方式への移行が
前提条件になる。
